= ADR-0016: deployment model, and who signs a team edit
:sectnums:

== Status

*Accepted* (2026-09-03). Rules *D-2* (deployment model) and *D-3* (commit
identity) from the roadmap's owner-decision table. This is the ADR that
link:0002-authentication-strategy.adoc[ADR-0002] defers to when it parks
GitHub App authentication "to the deployment-model ADR", and it is the
precondition every Phase 7 package was blocked on.

The two rulings are the owner's. The four consequences in
<<consequences-already-approved>> are the roadmap's recommendations, adopted
here because D-2 selects them; they are reversible. The two rows in
<<what-is-not-known-yet>> are *not* decided and must not be read as facts.

== Context

BerryWiki today has no user, no session and no login. There is exactly one
outbound credential, read from `BERRYWIKI_GITHUB_TOKEN`, and every commit
carries one identity: the process's own. That is correct for the Solo shape
and cannot survive a second editor.

Two questions had to be answered before a single Phase 7 route could be
written, because each of them changes the shape of the code rather than its
configuration:

* *Where does BerryWiki run, and how many wikis does one process serve?* This
  decides whether `App` stays concrete over one store or has to become a
  registry, and whether state is one directory or a per-tenant tree.
* *Whose name is on a commit when a logged-in person saves through a shared
  server?* This decides whether the server needs per-user credential storage,
  which is the difference between a configuration file and a secret store.

Everything else in the deployment picture follows from those two.

== Decision

=== D-2: on-prem, one team, one wiki

BerryWiki is deployed *on premises, by the people who use it, as one server
process serving one wiki to a handful of trusted editors on a private
network.* This is option (a) of D-2. Hosted multi-tenant SaaS is not built and
is not designed for.

Concretely:

* There is no tenancy boundary, because there is one tenant. `App`, `Ctx` and
  `route` may stay concrete over a single store; the multi-wiki registry work
  (P8-registry) is *not* authorised by this ADR and needs its own ruling.
* The isolation boundary is the machine and the private network, not the
  process. BerryWiki is not a security boundary between organisations, and no
  document may claim it is.
* The URL space stays single-wiki. There is no `/w/<slug>/` prefix.
* "Enterprise" is a *deployment guide*, not a product tier with a separate
  build. One binary, one core, the Solo contract passing throughout.

The reason to prefer this over an org-wide or hosted shape is that it is the
only one whose security story BerryWiki can actually tell. A hosted service
holding many organisations' wikis would need BerryWiki to be the isolation
boundary, and nothing in the codebase has been built or reviewed to be one.
On-prem moves that burden to the network operator, who already carries it.

=== D-3: the author is the person, the committer is the service

When a principal saves a page through a Team-profile server, the commit
carries:

[cols="1,3"]
|===
| Field | Value

| `GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL`
| The human principal, from the identity map in Team config.

| `GIT_COMMITTER_NAME` / `GIT_COMMITTER_EMAIL`
| The service identity. Always. The service is what actually holds the push
  credential, and saying otherwise would be a lie in the audit trail.

| `BerryWiki-Principal:` trailer
| The principal as BerryWiki knows them, in the commit message body.
|===

This is option (a) of D-3, with the author field used rather than a
`Co-authored-by` trailer, because git's author field is the one that survives
every tool that reads history.

*Why all three and not one of them.* Author alone is forgeable by anyone with
the push credential and says nothing about which system produced the commit.
Committer alone erases the person. The trailer alone is invisible to
`git log --format=%an`. Together they answer three different questions: who
wrote it, what put it in the repository, and what BerryWiki believed at the
time. The third matters because the first two are git's fields and can be set
by anything; the trailer is the one BerryWiki writes about itself.

*Rejected: per-user tokens (option b).* Incompatible with the design as built.
There is one clone and one process, and the push credential is process-wide;
per-user push would need a clone or a credential switch per principal. It also
turns the server into a store of other people's GitHub tokens, which is a much
larger security burden than the feature is worth for a single team.

*Rejected for now: GitHub App user-to-server tokens (option c).* Not
foreclosed, but it needs an HTTP client for the one-hour refresh, which is a
dependency-tree decision (D-4), and its behaviour against `.wiki.git`
specifically is unverified. Revisit only after P9-spike-enterprise.

*The mechanism already exists.* `GitRepo::exec` sets `GIT_AUTHOR_*` and
`GIT_COMMITTER_*` from the repository's `Identity` and then applies
`extra_env` *after* them, so a per-request `with_env` override replaces the
author while the committer stays the service. No change to the git engine is
needed to implement this ruling, only a caller that uses it. Verified by
reading `exec` in `crates/berrywiki-git/src/lib.rs` on 2026-09-03; the
ordering is the load-bearing detail, so a test must pin it rather than relying
on the reading.

[[consequences-already-approved]]
== Consequences that follow from D-2

These four were recommended in the roadmap and are adopted here because D-2
selects them. Each is reversible and each is cheap to reverse.

. *Authentication is the reverse proxy's job.* Team profile trusts a
  `Remote-User` header, and only from an address inside `--trusted-proxy`.
  BerryWiki terminates no TLS, stores no password for this path, and issues no
  cookie. On-prem single-team is exactly the case where an existing SSO proxy
  is already present or trivially added. The Solo profile ignores identity
  headers entirely, and the Solo contract asserts that.
+
The page-password path in link:0015-import-formats-and-dependency-doctrine.adoc[ADR-0015]'s
sibling access-control work is a separate mechanism and is not affected.

. *State stays outside the clone,* under `$XDG_STATE_HOME/berrywiki/<repo-id>/`
  as link:0008-safe-mutation-and-app-state.adoc[ADR-0008] already specifies.
  One wiki means one state directory; no per-tenant root is needed. A systemd
  unit must set `XDG_STATE_HOME=%S/berrywiki`, because `state_base()` falls
  back to the temporary directory when neither XDG nor HOME is set, and a
  `DynamicUser=` unit would silently lose drafts on restart.

. *Config is hand-rolled, and the profile is a ceiling.* The reader uses the
  same sections-and-scalars grammar as the metadata parser, so no
  configuration-format dependency enters the tree. `berrywiki serve <dir>` is
  Solo and *refuses* a config file, a non-loopback bind, or an identity header;
  `--profile team --config <file>` unlocks them. The profile names a maximum,
  never a minimum.

. *Tamper-evidence is conditional, and the condition is stated in the UI.*
  A signed history is only evidence if the remote refuses rewrites. On an
  on-prem remote that is a pre-receive hook and is achievable. On a GitHub
  `.wiki.git` it is unknown (see below). Until it is known, no document,
  README or route may describe the audit trail as tamper-evident without
  naming the condition in the same sentence.

[[what-is-not-known-yet]]
== What is not known yet

Both rows are hypotheses. Neither may be cited as a fact, and each carries a
row in `docs/compatibility/github-wiki.adoc` until a credential-gated spike
runs.

[cols="2,3,1"]
|===
| Question | Why it matters | Spike

| Does GitHub attribute a commit to a user account when the author email
  matches that account, on a `.wiki.git` push made with a different account's
  token?
| If it does not, the author field is correct in git and invisible on
  github.com, and the trailer becomes the only attribution a reader sees
  there. That changes what the audit page can promise.
| P7-spike-team

| Does a `.wiki.git` repository support branch protection, or any rewrite
  refusal at all?
| Consequence 4 rests on it. If wiki repositories accept force-pushes
  unconditionally, then signed commits on a GitHub-hosted wiki are evidence of
  authorship only, never of an unbroken history.
| P9-spike-enterprise
|===

== Consequences

* Phase 7 is unblocked. P7-headers, P7-identity, P7-authz, P7-config and
  P7-drafts-principal may start; each still needs its own evidence row.
* P8-registry and the multi-wiki URL space are *not* unblocked. They need a
  re-ruling of D-2, because this ADR rules them out rather than deferring them.
* link:0002-authentication-strategy.adoc[ADR-0002]'s deferral now points at a
  document that exists. Its GitHub App question is answered "not now, and here
  is what would have to be true first".
* The identity map is a new piece of Team configuration and therefore a new
  piece of the config grammar. It holds names and email addresses, never
  secrets.
* A test must assert `%an` and `%cn` on a team save, and must assert the
  trailer, because all three of them are separately forgeable and separately
  droppable.
