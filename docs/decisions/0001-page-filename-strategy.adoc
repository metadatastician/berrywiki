= ADR-0001: Page filename strategy
:sectnums:

== Status

*Accepted* 2026-09-15, after the live GitHub Wiki compatibility spike this ADR
was blocked on. Evidence is recorded in
link:../compatibility/github-wiki.adoc[the compatibility report].

The spike *confirmed the premise*: the native GitHub wiki UI renders no
directory hierarchy, so a flat scheme was the right call. It also *measured a
cost this ADR did not anticipate*, recorded under <<_consequences>> — the
decision is accepted with that cost stated, not in spite of it.

== Context

BerryWiki presents a hierarchical notebook, but the canonical store is a
GitHub `.wiki.git` repository whose native web UI does not render real directory
hierarchy. The product requirement for Phase 0 is that *the native GitHub wiki
reader must work* for users without BerryWiki.

The tree must be derived from stable page ids + `parent` metadata, never
inferred from filenames. Filenames therefore only need to be stable, unique,
GitHub-renderable and rename-tolerant.

== Decision

Use *flat, `--`-separated filenames* that encode the logical path for human
legibility, e.g.:

----
Teaching--Course-A--Assessment-Plan.md
----

* The hierarchy of record is the `parent` id chain in metadata.
* The filename is a human-friendly slug, not a source of truth.
* Collisions are resolved deterministically by appending a short id suffix
  (`Assessment-Plan--e256.md`) only when needed.

== Alternatives considered

. *True nested directories* (`Teaching/Course-A/Assessment-Plan.md`) — rejected
  because the native GitHub wiki UI does not present them as navigable
  hierarchy, and `[[WikiLink]]` resolution appears to be title-global.
+
NOTE: The 2026-09-15 spike confirmed the *sidebar* is what produces navigable
hierarchy in the native UI, which holds regardless of on-disk layout. It did
*not* directly test whether nested directories render acceptably — that
specific alternative remains unmeasured, and this rejection still rests on the
original reasoning.
. *Opaque id filenames* (`0195f6ec….md`) — maximally rename-safe but unreadable
  in a plain checkout and in GitHub's page list; violates "usable without the
  app". Rejected.
. *Title-only filenames* (`Assessment-Plan.md`) — collides across branches of
  the tree with duplicate logical titles. Rejected as the default.

== Consequences

* Renames change the filename but not the id, so links keyed on id survive; link
  *text* rewriting is a separate, configurable operation.
* The `--` separator must be escaped/normalised in titles that literally contain
  `--`.
* *Measured 2026-09-15 — the github.com title cost.* GitHub substitutes
  *each* `-` in a filename with a space when deriving the page title. It
  attaches no special meaning to a doubled hyphen. So `Editing--Attachments.md`
  is titled *"Editing␣␣Attachments"* on github.com — a literal double space —
  and every additional path segment adds another. Control:
  `Getting-Started.md` titles as "Getting Started", exactly as expected.
+
The navigable hierarchy a reader sees in the native UI comes *only* from the
generated `_Sidebar.md`, never from the `--` in the filename. BerryWiki readers
see a clean tree; someone reading the same wiki on github.com sees a title with
doubled spaces in it.
+
This does not reopen the decision — the alternatives were rejected for reasons
the spike did not disturb — but it is a real, visible cost that the original
ADR assumed away, and any future scheme change should be measured against it.
