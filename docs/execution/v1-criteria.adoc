Until now nothing defined "v1". The only release gate was *MVP-declare*, which
cuts `v0.1.0` (link:../architecture/implementation-plan.adoc[implementation
plan], Phase 5 exit criteria). This document defines what `v1.0.0` must
additionally show. It is written so that *every criterion is a check that can
fail*: each names the evidence that satisfies it, and "we believe so" is never
that evidence.

== Release line

. *`v0.1.0`, MVP-declare.* Unchanged: the Phase 5 exit criteria and the
  MVP-declare package. It is the first tag, and it is a prerequisite here.
. *`v0.x`.* Each criterion below lands as its own increment, with the default
  branch green when it does.
. *`v1.0.0`.* Every row below is *met*, or *waived by a recorded owner ruling*
  that names the row and gives the reason. A row that is merely "nearly met"
  blocks.

== How a criterion is judged

* *Met* means the named evidence exists, can be re-run, and was produced at the
  candidate commit or after it. A count from `grep`, a warm `target/`, or a
  green check that has never been shown to fail does not qualify.
* Every automated gate cited here must carry a *planted negative*: a known-bad
  input that the gate is shown to reject, in CI.
* Numeric thresholds marked _(proposed)_ are the owner's to set. They are not
  met by being reported close.

=== S: security and adversarial robustness

[cols="1,4,4,1", options="header"]
|===
| ID | Criterion | Evidence that satisfies it | Now

| S1 | A written threat model covers every surface: the HTTP server, parsers of untrusted input (Markdown, the metadata block, CherryTree XML, multipart upload, request line and headers), the filesystem, git, the GitHub mirror and credentials. | `docs/architecture/threat-model.adoc`, reviewed against the route table and the crate list. | ❌
| S2 | The local server refuses cross-origin and rebinding attacks. | Tests that plant a cross-site `POST` (foreign `Origin`), a foreign `Host` header, and the `/\host` redirect form, each refused, and that fail when the check is removed. | ✅ `crates/berrywiki-serve/tests/provenance.rs` (6 end-to-end attacks, each with a same-origin positive control) and the `guard` unit tests; mutation-checked

== Not required for v1

Zim import and the other P6 importers; SPARK proofs (the invariants are
*tested*, not *proved*, and v1 says so); the generated-script enhancement layer
(ADR-0007); full-text search at scale; the Enterprise profile (P9). The Team
profile *is* in v1 (M1).

== Planned integrations (after v1)

Recorded on the owner's instruction (2026-10-05), for integration after v1.
None of them blocks v1. Each must keep the core invariants: the wiki stays
plain Markdown, it stays usable without BerryWiki, and no script is served.

* *Internationalisation:* UI strings and diagnostics translatable, using
  `hyperpolymath/polyglot-i18n`; right-to-left layouts covered by the
  accessibility gate.
* *Spell checking:* Hunspell (or Aspell) dictionaries, run server-side, with
  the language taken from page metadata. No client script.
* *AsciiDoc pages:* rendered through Asciidoctor beside Markdown, only where
  the native GitHub wiki also renders them.
* *Format conversion:* Pandoc as an import and export path (the P6-import-*
  packages already plan Pandoc; ADR-0015 governs the shell-out cost).
* *OCR:* text extracted from attached images and PDFs for search, never
  replacing the attachment.
* *Encrypted CherryTree notebooks* (`.ctz`/`.ctx`, 7-Zip AES-256): import with
  the password read from the terminal, decrypted in memory, no plaintext on
  disk. Refused in v1 by owner ruling (2026-10-05).
* *Multilingual corpora:* `hyperpolymath/lol` as a source of language data,
  for example dictionaries and language detection.
