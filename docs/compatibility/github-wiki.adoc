[IMPORTANT]
====
This report strictly separates *Verified*, *Assumption*, *Unverified* and
*Decision*. Do not treat an assumption as a fact.

*Updated 2026-10-05: the live spike has run.* Every live row except the
repository size limit and token authentication now carries evidence from the disposable wiki
`metadatastician/berrywiki-wiki-spike`, including two refutations: `.md` and
path-style links do not open the rendered page, and attachments are publicly
reachable by bare URL. Browser navigation to heading fragments was not tested,
and the token-authentication row is still untouched.

*Earlier, 2026-09-15: the live-GitHub column stopped being entirely untested.*
Publishing `metadatastician/berrywiki.wiki` and fetching the rendered pages
settled four rows below — three confirming the hypothesis and *one refuting
it*. The great majority of the column is still ❓, and the authentication row
in particular is untouched: that wiki is pushed over SSH, not with a token, so
link:../decisions/0002-authentication-strategy.adoc[ADR-0002] remains Proposed
on no evidence.

== Live GitHub Wiki behaviour

Each row is a concrete test against a real `<repo>.wiki.git`. The 2026-10-05
spike ran them against the disposable wiki
https://github.com/metadatastician/berrywiki-wiki-spike/wiki[`metadatastician/berrywiki-wiki-spike`]. Status codes were not taken as
evidence: a page that does not exist also answers `200` (it redirects to the
wiki home), so every result was checked by content. Two rows are still ❓: the
size limit and token authentication.

[cols="3,1,3", options="header"]
|===
| Question | Tag | Expected / hypothesis (to confirm or refute)

| Does a leading `<!-- berrywiki ... -->` comment stay invisible in the rendered wiki page? | ✅ | *Confirmed 2026-09-15; independently observed 2026-09-29 on a second consumer.* The original test found neither `<!-- berrywiki` nor `archived: false` anywhere in the raw HTML of three sampled live pages. On [blocky-writer's Home page](https://github.com/hyperpolymath/blocky-writer/wiki), the rendered page contains the content following the leading metadata comment but not the comment or metadata values. The page source and its metadata are maintained in [`wiki/`](https://github.com/hyperpolymath/blocky-writer/tree/main/wiki). That observation was made without `berrywiki check` (the reporter lacked Rust and crates.io access). *Checked 2026-10-06:* BerryWiki at `d9bb172` ran `berrywiki check` on blocky-writer's `wiki/` at `91a6c65` and on its published `.wiki.git` at `59b17bd`, which is byte-identical apart from `wiki/README.adoc`: 8 pages, 0 errors, 0 warnings, exit 0. `berrywiki sidebar` (without `--write`) reproduced the committed `_Sidebar.md` byte for byte. The same binary first reproduced the `fixtures/test-wiki` baseline (10 pages, 0 errors, 3 warnings), and a planted mutant of the blocky-writer tree (one page given another's `id`, plus a link to a missing page) gave 8 errors and exit 1.
| Do nested subdirectories render as navigable hierarchy in the native wiki UI? | ✅ | *Confirmed 2026-10-05 (spike).* No. A page stored at `nested/deeper/Nested-Leaf.md` is served at the flat URL `/wiki/Nested-Leaf` and listed flat in `_pages` as "Nested Leaf"; the directories are invisible. Hierarchy lives only in BerryWiki metadata and `_Sidebar.md`, as assumed.
| Are `[[WikiLinks]]` resolved by global page title, ignoring path? | ✅ | *Confirmed 2026-10-05 (spike).* Yes. `[[Nested Leaf]]` renders as `/wiki/Nested-Leaf` and opens the page stored two directories deep; `[[Spike Target Page]]` and `[[Spike-Target-Page]]` both resolve to the same page.
| Do `[[Page#heading]]` anchor links work? | 🟡 | *Partly measured 2026-10-05 (spike).* `[[Spike Target Page#Section Two]]` renders `href="…/wiki/Spike-Target-Page#Section-Two"` (case kept), while the heading's id is `user-content-section-two` (lower case). The plain Markdown form `[x](Spike-Target-Page#section-two)` emits `#section-two`. Neither fragment equals the id literally, and the spike did not test browser navigation for either (no browser), so do not treat anchor scrolling as verified.
| Do links with spaces / `.md` / no `.md` all resolve? | ❌ | *Refuted 2026-10-05 (spike): not all.* See the link-format matrix below. Bare names, `%20` spaces and `./` resolve to the rendered page; **a `.md` suffix 302-redirects to the raw Markdown** on `raw.githubusercontent.com` (`text/plain`), and **a path-style link** (`nested/deeper/Nested-Leaf`) dead-ends at `/wiki/nested`.
| How do case-only renames behave on GitHub's store? | ✅ | *Measured 2026-10-05 (spike), server side only.* `Case-Probe.md` → `case-probe.md` (two-step `git mv`) pushes cleanly; a fresh clone contains only `case-probe.md`; both `/wiki/case-probe` and `/wiki/Case-Probe` serve the renamed page, so page lookup is case-insensitive. Behaviour on a case-insensitive *client* filesystem was not tested.
| How should attachments be linked so they survive sync? | 📌 | Settled by link:../decisions/0011-attachments.adoc[ADR-0011]: page-id-keyed `assets/<page-id>/<filename>`, authored as an ordinary relative Markdown link and anchored at the root only at render time.
| Does a relative `assets/<page-id>/<file>.png` link render as an image in the native wiki reader? | ✅ | *Confirmed 2026-10-05 (spike).* `![pixel](assets/<page-id>/pixel.png)` renders as `<img src="assets/<page-id>/pixel.png">` and that URL returns the PNG (checked by content, not status). ADR-0011's layout stands.
| Does GitHub enforce a size limit on a `.wiki.git` repository, and what is the failure shape when it is hit? | ❓ | *Deliberately not tested.* Measuring it means pushing to a shared service until it refuses. 🟡 assumption unchanged: a limit exists; BerryWiki's 1 MiB per-file cap bounds growth, never the total.
| Does Git LFS work on a `.wiki.git` remote at all? | ✅ | *Observed 2026-10-05 (spike): no.* The LFS batch API at `<repo>.wiki.git/info/lfs/objects/batch` rejects a token (`403 Bad credentials`) that the same repository's main LFS endpoint accepts (`200`, upload action offered; nothing was uploaded). Not adopted either way: a pointer file is unreadable in the native reader.
| Is an attachment inside `assets/` reachable by URL from the wiki's own web UI? | ❌ | *Refuted 2026-10-05 (spike).* Not only via the blob view: the bare URL `/wiki/assets/<page-id>/pixel.png` and `raw.githubusercontent.com/wiki/<owner>/<repo>/assets/…` both return the PNG. Every attachment in a public wiki is publicly fetchable by URL, which strengthens the §3.8 point: a read lock exists only where BerryWiki is the read path.
| How does `_Sidebar.md` behave / is it honoured? | ✅ | *Confirmed 2026-09-15.* The generated sidebar renders on every page fetched, not only `Home`. This is what carries BerryWiki's hierarchy into the native reader — see the filename row below, which is why it matters more than expected.
| Does pushing to `<repo>.wiki.git` with a token (not SSH) work, as ADR-0002 assumes? | ❓ | *Not tested.* The spike pushed with the operator's existing credentials and did not isolate token authentication, so link:../decisions/0002-authentication-strategy.adoc[ADR-0002] stays Proposed on no live evidence.
| How do concurrent pushes fail (non-fast-forward)? | ✅ | *Confirmed 2026-10-05 (spike).* The second of two pushes from the same base is rejected (`rc=1`, `! [rejected] … (fetch first)`); nothing is lost on the server. BerryWiki's fetch-before-push is required, as assumed.
| Does the default wiki branch have special behaviour? | ✅ | *Confirmed 2026-09-15.* A fresh clone of `<repo>.wiki.git` checks out **`master`**, not `main`, on a repository whose own default branch is `main`. This wiki's first commit ("Initial Home page", 2026-07-20) predates any tooling in this project, so `master` was not chosen here. Whether GitHub *always* creates wiki remotes on `master` is not established by this single observation — but tooling that assumes `main` is wrong at least here.
|===

== Filename strategy findings

See link:../decisions/0001-page-filename-strategy.adoc[ADR-0001]. Working
hypothesis given "native reader must work": flat `--`-separated filenames
(`Teaching--Course-A--Assessment-Plan.md`), because the native wiki UI does not
present real directory hierarchy.

=== Measured 2026-09-15: GitHub substitutes every `-` with a space

The premise survives; the *presentation* does not, and this was never checked.
GitHub derives a page's displayed title from its filename by replacing **each**
hyphen with a space. It attaches no meaning to a doubled hyphen. So:

[cols="2,2,1", options="header"]
|===
| Filename | Title shown on github.com | Tag

| `Getting-Started.md` | `Getting Started` | ✅ control — behaves as expected
| `Editing--Attachments.md` | `Editing␣␣Attachments` (a literal double space) | ⚠ cost
|===

Verified by reading `<title>` out of the raw HTML of both live pages; the double
space is present in the bytes (`cat -A`), not a rendering artefact.

*What this does and does not mean.* It does not reopen ADR-0001's decision: the
native UI still cannot show real hierarchy, which is the reason the flat scheme
was chosen, and nested directories remain untested (❓ above). What it means is
that the scheme carries a cosmetic cost on github.com that ADR-0001 does not
record — every nested page gets a visibly malformed title in the native reader.
Readers using BerryWiki, or following the generated `_Sidebar.md`, see the clean
tree and never encounter this.

This is worth stating plainly because it is precisely the class of thing that
only a live wiki could reveal, and it was found within minutes of exercising
one. It is an argument for finishing the Phase 0 spike, not a defect.

== Rendering fidelity (BerryWiki preview vs GitHub)

BerryWiki renders its preview with comrak GFM (`berrywiki-render`). Known,
deliberate differences from GitHub's wiki pipeline — all *safety-over-fidelity*
and none affecting the canonical source:

[cols="3,2", options="header"]
|===
| Aspect | BerryWiki policy
| Raw inline/block HTML | *Escaped/omitted*, never emitted (comrak `unsafe_=false` + `tagfilter`). GitHub renders a *sanitised subset* of inline HTML, so some GitHub-rendered HTML will not appear in BerryWiki's preview. ✅ tested.
| `javascript:` / `vbscript:` / non-image `data:` link URLs | Rewritten to `#` at the AST level. ✅ tested.
| Syntax highlighting of code blocks | Not applied (comrak default features off, to keep the dependency surface small). The original rustc-1.85 reason is retired — the workspace MSRV is 1.89 — but re-enabling is unmeasured. May return behind a feature.
| Exact GFM parity (tables, task lists, autolinks, footnotes) | comrak GFM; *parity with GitHub's exact output is UNVERIFIED* until the live spike (❓).
|===

Source remains canonical regardless; the preview is advisory.

== Open questions

* Exact anchor slug algorithm GitHub uses for headings (we implement a
  GitHub-compatible approximation; confirm edge cases with Unicode).
* Whether `_Sidebar.md` supports nested lists in the rendered sidebar to the
  depth we generate.
* Whether GitHub's client script scrolls to the heading for `#section-two` or
  `#Section-Two` when its id is `user-content-section-two`. Needs a browser.

== Recommendations

. Persist links in GitHub-native Markdown; accept `[[…]]` only as *authoring*
  input, serialised on save. Serialise to the *bare page name*: never a `.md`
  suffix (it opens raw Markdown) and never a directory path (it dead-ends), per
  the link-format matrix. Do not rely on a heading fragment for navigation until
  a browser test confirms it.
. Use flat `--` filenames; keep the tree in metadata, never infer it from paths.
. Keep the metadata HTML comment; its invisibility has now been observed on live
  GitHub Wiki pages in two repositories. Recheck if GitHub changes its renderer.
